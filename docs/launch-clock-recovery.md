# Launch clock and recovery journal

Journal version 1 retains serde-default fields for DAQ stamp, reset tombstone and new-cycle evidence; older saved journals do not acquire a reset implicitly. The launch clock has a durable authority, revision, launch-session identity and absolute UTC T0. Startup restores these values; it does not call the launch-clock setter, rotate the DAQ session, or calculate a new DAQ deadline. Idle/Startup telemetry, local state reset, simulation data reset and UI reconnect do not clear an active clock. Explicit ResetTClock creates a new session and retains previous sessions and recovery observations.

The default journal is `backend/data/launch-clock-primary.json` or `backend/data/launch-clock-rrls.json`. Configured station identities add a stable SHA256-derived station suffix. These paths depend on station/role, not mode, executable, version or build cache. Keep the service working directory stable, or set the absolute `GS_LAUNCH_CLOCK_STATE` path consistently in every mode. Primary and RRLS must have separate journal paths.

A reset tombstone survives restart. Repeated received Launch/Ascent/Landed packets and old Valve sequence status cannot start a reset clock. A new accepted operator launch, or a received prelaunch phase followed by Launch, re-arms the next countdown. Re-arming advances the clock revision before pilot/T0 so a delayed reset cannot clear an already accepted new cycle. Flight-state projection and hardware interlocks are unchanged.

DAQ's separate network-variable cache remains authoritative for its literal `[session, deadline]` and packet revision. Journal restoration occurs before network-variable initialization and preserves that exact payload/revision; conflicts fail rather than recompute or overwrite a deadline. A legacy active DAQ cache without an explicit saved T0 is marked unknown, not interpreted using an assumed cutoff duration. An explicit reset is required before authoring a replacement clock. The DAQ cache and journal are two files, not a cross-file atomic transaction; an interrupted reset preserves the existing literal cache instead of extending it.

## Persistence and errors

One background writer owns journal serialization, file synchronization and atomic rename. It keeps one pending latest snapshot; every snapshot contains all accumulated observations/session history, so coalescing clock updates does not lose events. New disk work never runs inside SDK callbacks or clock/radio locks. Existing DAQ network-variable commits retain their existing behavior. User reset and recovery APIs await the captured persistence ticket outside locks; a failed write returns an error and notification, not a durable acknowledgement. Graceful shutdown closes journal admission and captures its final ticket under the same history lock, then flushes outside locks; detached metadata tasks cannot enqueue past that barrier. Bounds are 4096 observations, 1024 old sessions and 4 MiB serialized journal; full history requires export/archive rather than silent eviction.

Unreadable journals are held unknown and never silently replaced; the original is copied aside on an explicit successful reset attempt. Unknown/corrupt primary state cannot advertise a fresh Idle clock and erase an observer's retained TPlus. While a process runs, recovery elapsed time uses its monotonic bridge to T0, so a host UTC correction does not change the elapsed observation. Process restart uses absolute UTC T0; reliable elapsed recovery across restart therefore requires valid host UTC. The existing dashboard's clock display still uses its normal UTC presentation.

## Primary/RRLS synchronization

The `TC` clock extension uses the existing bounded SETTINGS transport and its aggregate byte allowance, not a reserved SEDS type/endpoint or an SDK packet. Existing `OM` operating-mode and document formats are unchanged. The ACK-capable clock profiles use `TC03` (signed) and `TC04` (transport-validated display metadata). Query and Reply explicitly negotiate `ack_supported=true`; old private TC01/TC02 frames are demultiplexed and rejected. Public older backends have no clock profile. Initial capability discovery is bounded to three accepted queries/hints, so unsupported peers do not cause endless probing. Queue refusal does not spend an attempt. For a positively negotiated peer, the primary retains only the newest dirty authority/revision and retries hints with 5/10/20/30-second backoff (30-second maximum interval) until an explicit matching revision ACK. The observer ACKs only after durable journal application; lost ACKs are regenerated from matching hints. Once confirmed, stable peers send no clock traffic. Negotiated capability is scoped to the primary HEALTH session, not the SETTINGS-presence lease. In direct mode the primary may have no READY/settings presence: only a known peer's dirty hint uses the same bounded validated-metadata admission as query replies. This neither creates nor refreshes a lease/settings presence, and unknown peers do not gain that admission. The four bounded outbox classes share the original byte allowance and radio queue limits. This introduces no MCU state or SDK ABI change.

Replies require the current primary HEALTH session and a fresh nonce. Acknowledgements require the negotiated capability, current session and exact current authority/revision. Disk failure, stale ACKs and old clock contracts cannot confirm a new revision. Where installation pairing is configured, its existing signature and issuer/recipient checks are mandatory, with no unsigned downgrade on invalid configuration. Otherwise the extension uses the existing unpaired command transport's HEALTH/session boundary. Neither valid nor malformed clock envelopes refresh HEALTH, command leases or general settings presence, and SETTINGS payloads never fall through to SEDSnet.

RRLS retains its clock during disconnect and never authors one from observed flight-state packets. A fresh primary revision can clear retained TPlus after an explicit primary reset. Lower revisions, equal-revision conflicts and stale challenges are rejected. A new unknown primary Idle revision zero cannot clear a saved active clock.

Authenticated RRLS operators with SendCommands and ResetTClock command access can request reset through the existing HTTP or WebSocket command path. There is one bounded pending request carrying the exact expected authority/session/revision/clock. Offline/pending requests retain the clock and are visibly pending. The primary checks that contract atomically, resets, and flushes its journal before a positive reply. An unchanged failed reset can retry the same positive contract without another generation; a new launch invalidates it. Failed reset writes cannot escape through ordinary clock queries or hints. Requests retry finitely; no reply is reported as a successful reset. Pending requests are process-local and may be lost on RRLS restart; the durable clock and audit are retained and synchronization resumes.

## Recovery observation API

`GET /api/recovery` requires ViewData and advertises explicit `recovery_marker_supported` and `clock_reset_request_supported` capabilities. Older backends omit them; the new frontend defaults them to false. New status fields are optional to the frontend, and old frontends can continue using the original clock and command APIs.

`POST /api/recovery/reached` requires an authenticated named operator with SendCommands. Its only body is `{"launch_session":"…"}`; a stale session is rejected. The server records its UTC, signed T-relative elapsed, canonical T0/revision, operator, SHA256 authentication-session fingerprint and station. It never records the bearer secret and never enqueues a telemetry/output command. Repeating a mark at the same station/session returns the original event, actor and time. Reset keeps old events separate from the new session.

`GET /api/recovery/export.json` and `/api/recovery/export.csv` require ViewData and export the audit. JSON includes session history; CSV includes event identity, session/authority/revision, UTC/T-relative milliseconds, actor/session fingerprint, station and whether the clock was freshly primary-verified. Recovery marks are currently local to each station; clock synchronization does not assert or propagate another station's operator identity. Export each station's audit when combining records.
